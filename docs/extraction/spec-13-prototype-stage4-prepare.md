## 3. Prerequisite refactors

**Order (decided here; resume plan section 4).** The steps run in this order: P0, P1, P2a, P5a, P2, P3, P4, P5b, P6, P7. Each is one PR, and each runs the gate (section 9) and the tests named for it. P7 does not depend on P6, so it may run earlier, as resume plan step 4 says; it stays listed last in the order.

- P1 is a package move with no behaviour change, so later diffs stay small. It changes no Temporal workflow or activity type name and no JSON payload.
- P2a comes before any step that gives `TransitionFired` work. Today the relay does not claim it, and both automation adapters throw on it (`OutboxPort` lines 16–17; `AutomationPort` lines 37–42). Without P2a, the proof tests of P2 to P4 cannot pass.
- P5a comes after P2a and before P2, because the relay must run the recompute before the ingress whatever the ingress is.
- P2 to P4 each remove one kind's producer and its consumer in one PR: actions, then timers, then signals. P5b changes the consumer: `AutomationPort` takes Store events. P5b comes after P2 to P4, because until then the relay still dispatches `ActionRequest`, `TimerScheduled`, `TimerCancelled` and `SignalReceived` through the switch.
- P6 and P7 are the read side. P6 moves `read` and `browse` onto their own ports and switches index preparation to the host use case. P7 separates the index DDL and does not depend on P6. Its Command-side backfill is called from today's host paths (`IndexPreparingOntologyAdministration.prepareIndexes`, line 81, and `OntologyStartupValidator.run`, line 65), and P6 moves those calls into the use case later. P7 is held until the owner confirms B4 (section 12).
- Alternative, the owner's choice: merge P2, P3, P4 and P5b into one PR. P5a stays where it is, after P2a. The proof tests then run once, at the merged PR. The holds below still apply to the merged PR.

**Mixed versions at P2 (N11).** P2, P3 and P4 deploy without overlap. Stop writes and the old relays, confirm with O-3 that the step's kind is drained, then start the new version, which runs that step's migration at startup. No old and new relays run together. Before P2 lands, the previous code writes `TransitionFired` rows without `self`, and their `ActionRequest` siblings share `occurred_at` with them (lines 347 and 351 both use `now`). Once P2 drops the kind, new pods cannot claim those siblings. So a `TransitionFired` row without `self`, written before the stop, runs no actions in the new relay and is marked processed. Its actions are its siblings, which the old relay dispatched before the stop. Failing on such a row would block the relay (`OutboxRelay` javadoc lines 90 to 96). **Redelivery (N7, driver decision).** `AutomationPort` promises that a second call with the same `entry.id()` does not invoke the handler again (javadoc lines 29 to 31). `InProcessAutomationPort` records `entry.id()` before it dispatches (line 115), so a failure part-way through a row's actions loses the remaining actions on retry. Since P2, one `TransitionFired` row holds several actions. P2 therefore records each action under (entry.id(), action index), with the timing rule that follows. In-process, an action's class is its type in the sealed `org.sequeless.ontology.automation.api.Action` (automation-contract 0.1.0; four permitted records; checked with `javap` on the released jar, since the contract's source is not in this repo, and `DefaultTransitionService` imports the four types at `origin/main` lines 30 to 35). `SetPropertyAction` and `CreateObjectAction` are Store actions: `DefaultActionExecutor` commits them through `ObjectStorePort.commit` (lines 121 and 166) inside the claim transaction, so they are not recorded until the claim commits. They commit with the claim, which marks the row processed, or they roll back with it and re-run. `LogAction` is local: it writes no Store row and makes no external call. `WebhookAction` is non-transactional: its HTTP call cannot roll back with the claim. `LogAction` and `WebhookAction` are each recorded under (entry.id(), action index) as soon as they succeed. A retry runs, in index order, every action that is not recorded. The adapter's switch over the sealed type is exhaustive, so a new action type does not compile until it is classed.

After P2 removes the `actionKind` payload string, the adapter gets each action's type and index from the row. The `TransitionFired` row carries the frozen `self` snapshot, `typeIri` and the machine IRI. The adapter rebuilds the action list from them, through the automation-contract of the version B2 selects, in the order that contract builds it. An action's index is its position in that list, and its type is the class of its sealed record. Both are derived, not stored, so a retry rebuilds the same list and the same indexes. This matches the Temporal key in P2 (C6). The alternative, not chosen, records the row only after all its actions and makes each action idempotent (section 12, R2).

**P5a transaction boundary and mode (N8, driver decision).** The relay claims a row inside a `TransactionTemplate` (`PostgresOutboxPort` line 53). The recompute's store writes use `PostgresObjectStore`'s REQUIRED template (line 67), so they join the claim transaction. A `StaleObjectException` that `DefaultDerivationRecomputer` retries can then mark the claim transaction rollback-only. The in-process default, COALESCE mode (`InProcessRecomputeProperties` line 58), runs the recompute on its own thread (`RecomputeCoordinator` line 87, the submit; line 120 is the thread factory), outside the claim. The ingress needs the recomputed `openTaskCount`, so P5a cannot use that path. P5a runs the recompute synchronously. `CoreConfiguration` gives the `DerivationRecomputer` bean the relay calls an `ObjectStorePort` decorator whose `commit` runs in a REQUIRES_NEW `TransactionTemplate` over the persistence `DataSource`. Reads delegate unchanged. A recompute commit survives a later rollback of the claim and is re-run without effect (commit-only-if-changed, `DefaultDerivationRecomputer` line 205). Core keeps its retry loop and gains no Spring dependency. The claim transaction holds only the claim and the processed mark. The ingress keeps today's boundary. RETRY_ONLY mode already runs inside the claim transaction, and it is the alternative (section 12, R3).

**C5 design (driver decision, revised for B4; the navigator's choice; the owner confirms it (section 12)).** V2 cannot move whole. Under B4 as proposed, its column, function and trigger are Command side, and its registries and GIN index are Query side. V2's file is not edited, because its checksum is recorded on every database that ran it. The split works like this.

**Recorded decisions, for the owner to review (R1 to R4).**

- R1 (N12, refetch). P4 changes the UI text at `object-signals.ts` line 47 but not the 1500 ms refetch (line 21). The refetch is correct after a synchronous commit: it is a wait, not a race. Removing it is a UI cleanup for a later PR, not a requirement of spec 13.
- R2 (N7, redelivery key). The key is (entry.id(), action index), recorded per action. In-process, an action's class is its type in the sealed `org.sequeless.ontology.automation.api.Action` (automation-contract 0.1.0; four permitted records). `SetPropertyAction` and `CreateObjectAction` are Store actions: `DefaultActionExecutor` commits them through `ObjectStorePort.commit` (lines 121 and 166) inside the claim transaction, so they are not recorded until the claim commits. They commit with the claim, which marks the row processed, or they roll back with it and re-run. `LogAction` is local: it writes no Store row and makes no external call. `WebhookAction` is non-transactional: its HTTP call cannot roll back with the claim. `LogAction` and `WebhookAction` are each recorded under (entry.id(), action index) as soon as they succeed. A retry runs, in index order, every action that is not recorded. The adapter's switch over the sealed type is exhaustive, so a new action type does not compile until it is classed. The Temporal key is unchanged by this rule. The alternative, recording the row only after all its actions with idempotent actions, is not chosen. The Temporal side already uses (event id, action index) (C6), so one key serves both adapters.
- R3 (N8, recompute mode). P5a runs the recompute synchronously, with each store commit in REQUIRES_NEW through the decorator in `CoreConfiguration` (section 3), and does not use COALESCE on the relay path. RETRY_ONLY, which runs inside the claim transaction, is the alternative. The owner may choose it, at the cost of the stale-object risk named in section 3.
- R4 (C7, signal rejection). A type-valid signal with no transition from the current state, or with a failing guard, returns 409 instead of 202 (P4; section 7.1). It is a REST behaviour change, listed here for owner review with R1 to R3.

O-17 (side effects aimed at a Store) is not open. #20's resolution point 5 decides it: the outbound port belongs to automation, and the host binds it to store-core's Store Command port. Section 3 records the decision. This spec keeps today's path.
