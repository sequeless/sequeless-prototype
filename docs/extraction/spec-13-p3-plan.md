## 3. The new data path

Today (P2d). `commitTransition` (314-351) puts one `TransitionFired` row in the outbox and, through `addTimerOutboxEntries` (346), one `TimerScheduled` for each timer transition that departs `toState`, and one `TimerCancelled` for each that departs `fromState`. All of it goes in one `ChangeSet` (348). The relay claims both timer kinds (`OutboxRelay.java:58-59`), and the adapter schedules or cancels.

After P3 (spec row P3, line 92, and #20 point 6):

- A move writes only `TransitionFired`. Its payload (`transitionFiredEntry`, 444-464) holds `objectId`, `tenantId`, `principalId`, `transitionName`, `fromState`, `toState`, `ontologyVersion`, `self`, `typeIri` and `machineIri`.
- The row does not hold the timer transition's name or its `after`. Both come from the behaviour: `timer.after()` is read at 407 today. The timer key stays `objectId|state|transitionName` (`timerKey`, 436-438).
- The lookup loop (371-381) moves to `DefaultTriggerEvaluator` (O-2). It reads the machine from the behaviour, as `onSignal` does (171-173), and selects the `TimerTrigger` transitions that depart `toState`. Which version it reads is open question 5, decided: the lookup reads the active behaviour and fails the dispatch on a version mismatch with the row's stamp, and that failure counts toward DR-23's three failures.
- Readers of the row after P3: the relay (`OutboxRelay`, unchanged for `TransitionFired`), and `InProcessAutomationPort.dispatchTransitionFired` and `TemporalAutomationPort.startTransitionFiredActions`. Both read `ontologyVersion`, `machineIri`, `fromState` and `transitionName` today.
- Zero-action transitions. Both adapters start nothing when the transition has no actions: the loop at `InProcessAutomationPort.java:177` runs zero times, and `TemporalAutomationPort.java:120-121` says so. The timer start must sit outside that loop, or a transition with only a timer would lose its timer. This plan puts it before the loop, so a throwing action cannot block it (open question 10, decided).
- Cancellation. The row's `fromState` says an object left a state, but a cancel needs the timer key, which needs the same lookup on `fromState`. The spec says `TimerCancelled` has no reader after P3 (row P3). The only guard left is the staleness check (`DefaultTriggerEvaluator.java:143-152`). Decided under open question 1: no cancel after P3.
- Start time. The in-process scheduler starts the clock at dispatch (`InProcessTimerScheduler.java:66`), and Temporal starts the workflow at dispatch. P3 does not change when the clock starts.

## 7. Risks

1. In-flight timers. In-process timers live in memory and are lost at a stop (`InProcessTimerScheduler.java:19-22`). Temporal timers can wait 72 hours (`reference.ttl:310`). The mixed-version procedure applies (spec lines 100-108): stop writes, drain every claimed kind, then wait for or terminate the running timers. Terminating needs the owner's written acceptance of the loss (spec line 105). For running Temporal timers, open question 11 (decided) avoids termination on replay grounds; see risk 2 and open question 19 for the dev-stack gate.
2. Replay. `TimerWorkflowImpl.run` changes its body (open question 1 removes the cancel await). A running old execution replays its recorded history under the new code, and a changed workflow can fail on replay. Open question 11, decided: `run` keeps its `(OutboxEntry, Scope)` input, so recorded histories still decode, and `Workflow.getVersion` guards the body change (item 14). No drain or terminate of running `TimerWorkflow` executions (the O-4 half of spec step 4); the O-3 row drain stays. P3 adds a `WorkflowReplayer` test (open question 21, decided; item 23b).
3. Memory. With no cancel (open question 1, decided), and without `TimerCancelled`, a timer stays pending until it is due, up to 72 hours per hold, and then no-ops at the staleness check. Pending entries for objects that left the state pile up in the in-process map, and a restart drops them.
4. Re-hold on Temporal (read from the code, not run). A second entry into the same state for the same object has the same `timerKey`, so the same workflow id. `workflowOptions` uses REJECT_DUPLICATE (199), which refuses that id even after a closed run (javadoc 42-51). `startTimerWorkflow` catches the error and does nothing (174-176). The re-hold keeps the first timer's remaining time only when the re-hold comes before the first run is due. If the first run has already closed, REJECT_DUPLICATE gives the second hold no timer at all. Today the first run is cancelled on leaving, so a second hold gets no timer on Temporal. The adapters already diverge today: the in-process path removes the timer on cancel (`InProcessTimerScheduler.java` line 78, reached from `InProcessAutomationPort.java` line 138) and re-puts a fresh 72 hours on the re-hold, while Temporal gets no timer. Without open question 17, after P3 a re-hold that comes while the first timer is pending would make the in-process adapter overwrite the pending entry (`InProcessTimerScheduler.java:66`) and give a fresh 72 hours, while Temporal keeps the remaining time, so the adapters would diverge. Open question 17 changes this: `putIfAbsent` makes the in-process adapter keep the pending entry, so the pending case no longer diverges; the closed case still does. The one resume test (`AutomationEndToEndTest.java:231`) resumes once and never holds again. Open question 2, decided (section 8): keep `timerKey` as the id and accept the divergence. After P3 (open question 17), a re-hold while the first timer is pending keeps the first timer's due time on both adapters. That is not a fresh 72 hours: the timer fires at the first hold's due time, which can be only an hour into the second hold. The closed case is unchanged. Open question 17 asks for this to be confirmed at the P3 code review; it follows from that decision and is not a new one.
5. Zero-action transitions. A timer that depends on actions would be lost (section 3). The test in section 6 covers it.
6. Dead-lettered rows (DR-23). After three failed dispatches a row is dead-lettered. Its timer and its actions then never start, and nothing retries it. A stamp mismatch counts toward the three (DR-23, line 158).
7. B2 wording (section 1). Settled: the timer path follows DR-23, as open question 6 records.
8. In-process re-arm on a retried `TransitionFired` row. The in-process port does not gate `TransitionFired` by the `dispatched` set (`InProcessAutomationPort.java` lines 123 to 127), and the per-action record (`dispatchedActions`) covers only the actions. After P3 the timer start sits in `dispatchTransitionFired`, outside the action loop (section 4, item 11), so a retried row calls `schedule` again, through the put at `InProcessTimerScheduler.java` line 66, with a fresh due time. Open question 17 changes the put to `putIfAbsent`, so the retry keeps the original due time. Temporal's start error is caught today at `TemporalAutomationPort.java:174-176`; item 16 carries that catch into `startTransitionFiredActions`, so the same retry is a no-op there. Open question 17.
