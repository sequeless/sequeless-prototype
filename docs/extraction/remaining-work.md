- [x] **Open risk: a persistent recompute failure blocks the relay.** Since P5a, the relay runs the recompute for each object-lifecycle row inside the claim, before dispatch. When the recompute exhausts its retries, any exception from the recompute propagates out of the claim handler. Running out of retries on contention is transient; a deterministic exception is the persistent case. `OutboxRelay.pollOnce` then stops, and the same oldest row fails again on every tick, so every row behind it waits. There is no dead-letter or skip path. Dropping the REQUIRES_NEW decorator (the alternative that spec 13 records) does not remove this, because the recompute stays synchronous in the relay. No remedy is in place. A remedy needs an owner decision: a dead-letter or skip in the relay. The risk is recorded in the P5a commit message (`6e7764f`) and in resume plan section 8. Remedy decided 2026-11-12 by the Navigator, under the owner's delegation: dead-letter, not skip. Plan: resume plan section 13, step 4. The open item stays until that PR merges. - [x] **BrowsePort id order is not one order across adapters (latent).** `InMemoryBrowsePort` orders ids with signed `UUID.compareTo` (its `CREATED_AT_THEN_ID` and `ID` comparators), while Postgres orders the `uuid` column unsigned, bytewise (`PostgresQueryStore` `ORDER BY created_at, id`). The two disagree on about half of random id pairs. No contract test has a tie today, so both adapters pass. `paginationOverUnionOfTypesIsOrderedByCreatedAtThenId` in `BrowseContract` names an id tie-break it never exercises. Recommended: (1) define the id order in the `BrowsePort` javadoc as unsigned byte order of the 16-byte uuid, which equals the lowercase canonical string order; (2) make both `InMemoryBrowsePort` comparators unsigned; (3) add a contract test with fixed ids on either side of the sign bit (for example `7fffffff-ffff-4fff-bfff-ffffffffffff` and `80000000-0000-4000-8000-000000000000`), with equal createdAt, for the default order and an explicit sort. Random ids would fail on one adapter about half the time, so use fixed ids. The order definition is a contract decision: owner or Navigator. Source: spec 13 P6a follow-up review, confirmed by a read-only review on 2026-11-12.
